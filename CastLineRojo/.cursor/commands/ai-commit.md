# AI 生成 Commit 并提交

你是本仓库的助手。用户希望**用 AI 根据当前改动生成本次 Git 提交说明**，并**实际执行 `git commit`**。默认**不要向用户确认是否暂存**；只要存在可提交的改动，就一路做完。

## 执行步骤

1. **收集变更（必须）**
   - 在项目根目录执行：`git status`
   - 查看已暂存变更：`git diff --staged`（或 `git diff --cached`）
   - 理解未暂存改动：`git diff`；对未跟踪文件按需阅读关键片段。

2. **决定提交范围（自动，不询问）**
   - **若已有暂存（staged）文件**：仅根据已暂存内容撰写 commit message，然后执行 `git commit`。
   - **若没有任何暂存，但存在未提交改动**（已修改或未跟踪）：在项目根执行 **`git add -A`**，再根据暂存后的 `git diff --staged` 撰写说明并执行 `git commit`。尊重 `.gitignore`，被忽略的不会被加入。
   - **若工作区干净**（无已修改、无未跟踪）：说明无需提交，不要执行 `git commit`。

3. **撰写提交说明**
   - 使用**完整句子**、语气与团队习惯一致；标题一行概括，必要时用正文说明动机与影响。
   - 优先**英文**作为 subject line（便于与 GitHub 生态一致）；若用户规则或对话中明确要求中文，则用中文。
   - 避免空话；说明「改了什么、为什么」；不要泄露密钥或隐私。

4. **执行提交**
   - 单行消息：`git commit -m "..."`（注意转义引号）。
   - 多行消息：使用 `git commit -F - <<'EOF'` 或 `git commit` 配合 heredoc，避免 shell 截断。
   - 提交成功后简短汇报：commit hash（若可得）、subject、是否还有未提交文件。

## 禁止

- 不要执行 `git push`、不要 `--force`，除非用户在本轮对话中明确要求。
- 不要在**工作区无任何可提交改动**时强行 `git commit` 或制造空提交。

## 失败处理

- `git commit` 失败（如 hook、身份未配置）：贴出错误摘要并给出可操作的下一步。
